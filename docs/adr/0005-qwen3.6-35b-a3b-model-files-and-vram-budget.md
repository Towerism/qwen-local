# ADR 0005: Qwen3.6-35B-A3B model files and VRAM budget

- **Status:** Accepted (2026-11-04)
- **Date:** 2026-11-04

## Decision

| Setting | Value |
|---|---|
| Place in the catalog | `qwen3.6-35b-a3b`, the default for fresh installs |
| Model file | `mradermacher/Qwen3.6-35B-A3B-GGUF`, `Qwen3.6-35B-A3B.Q4_K_M.gguf` (21,166,758,368 bytes) |
| Multi-token prediction (MTP) draft file | `ggml-org/Qwen3.6-35B-A3B-GGUF`, `mtp-Qwen3.6-35B-A3B-Q4_0.gguf` (1,060,038,432 bytes) |
| Vision | None. The pinned main repo has no vision projector (mmproj) file, so there is no `vision` profile |
| `agent` profile | 49,152 tokens of context, MTP on, every expert on the GPU, `vram_gib=21.8` |
| `long` profile | 262,144 tokens of context (the trained length), MTP off, the experts of 4 layers in system RAM (`--n-cpu-moe 4`), `vram_gib=21.7` |
| Everything else | As in the Qwen3.8-27B profiles ([ADR 0002](0002-model-file-and-vram-budget.md)): `q8_0` key/value cache, flash attention, one slot, `--fit off`, the same sampling, host, port and API key |

## Context

Qwen3.6-35B-A3B is a mixture-of-experts model: 35B parameters, of which about 3B are used per token (8 of 256 experts). On the RTX 4090 it generates code about 3 times faster than Qwen3.8-27B (343.1 against 114.4 tok/s with MTP on) and reads prompts about 3 times faster (7,723 tok/s at 16k tokens, against 2,171–2,474 tok/s from 2k to 48k); the 27B numbers are in [docs/architecture.md](../architecture.md). That speed is why it is the default for fresh installs. Qwen3.8-27B stays in the catalog, and an install that already runs it keeps running it until the user runs `qlm use qwen3.6-35b-a3b`.

Its Q4_K_M file is 19.7 GiB, against 15.3 GiB for the 27B file, so the 24 GB card has less room left for context. Moving some experts to system RAM (`--n-cpu-moe`) frees VRAM for context at a cost in generation speed. The profiles were chosen by measurement, as below: agent keeps every expert on the GPU and takes the largest context that fits with MTP; long takes the full trained context and offloads the fewest layers of experts that make it fit.

The main file and the MTP draft come from different repos, which is why every pin in `qlm/pins.py` carries its own repo and revision.

## Local copies (`qlm fetch --from`)

A user may already have one of these files on disk. `qlm fetch --from PATH` links it instead of downloading it, under these rules:

- The file must match the size and SHA-256 of a pinned file of the **selected** model. Select the model with `qlm use` first; a file of another model is refused.
- qlm creates a symlink in `~/.local/share/qlm/models/` and never copies the file, so the model doesn't take its 19.7 GiB twice.
- The linked copy must not be modified. qlm checks its size and SHA-256 when linking it and on each `qlm fetch`, but not when the server starts.
- A file that matches no pin is refused, and nothing is written. The files not given with `--from` are downloaded as usual.
- qlm never deletes what a link points at: `qlm uninstall --models` removes the link and leaves the user's copy.

## Measurements

Measured on 2026-11-04 on the RTX 4090 (24,564 MiB) with llama.cpp b11669 (`620d2225c`). With qlm-server stopped, the desktop held 1,478 MiB, which leaves 22.5 GiB. The load log reports `n_ctx_train = 262144` and 40 blocks (`qwen35moe`, 256 experts, 8 used per token). The main file and the MTP draft both load on this build, and the main file's weights take 19,903 MiB on the GPU.

A configuration fits when it starts, `qlm smoke` passes, and its peak VRAM from `qlm bench --quick`, rounded up to 0.1 GiB, plus the 0.5 GiB that `qlm start` keeps free, is at most the 22.5 GiB beside the desktop. Rounding first means `qlm start` accepts the profile's `vram_gib` on this desktop.

### Fit search

| Profile | Context | `--n-cpu-moe` | MTP | Result | Peak VRAM |
|---|---|---|---|---|---|
| agent | 65,536 | 0 | On | Starts and passes smoke; 22.1 + 0.5 GiB is over 22.5 GiB | 22.03 GiB |
| agent | 49,152 | 0 | On | Fits (chosen) | 21.77 GiB |
| long | 262,144 | 2 | Off | Out of memory allocating compute buffers at start | none |
| long | 262,144 | 3 | Off | CUDA error during warm-up; the server exits | none |
| long | 262,144 | 4 | Off | Fits (chosen) | 21.66 GiB |

Long starts its search at 262,144, the trained context, so smaller contexts weren't tried.

**MTP is on in agent.** The draft loads on b11669 and agent reaches 49,152 tokens with it at `--n-cpu-moe 0`, above the 32,768 floor, so the MTP fallback doesn't apply. MTP makes code generation 1.76 times and prose 1.36 times faster, for 1.1 GiB of VRAM. Long runs MTP off, like the 27B long profile; keeping 4 layers of experts in system RAM is what lets it hold the full 262,144 tokens, at 40 to 55% of agent's generation speed.

## Consequences

- **The VRAM margin is small.** `qlm start` needs the profile's `vram_gib` plus 0.5 GiB free: 22.3 GiB for agent and 22.2 GiB for long, out of 23.99 GiB. Either one is refused when the desktop and other apps hold more than about 1.7 GiB (agent) or 1.8 GiB (long). The desktop held 1,478 MiB when these were measured, and the KDE screen locker alone adds about 278 MiB while it runs. When `qlm start` refuses, it lists the processes holding VRAM: close what you can (browser windows are the usual ones), or run `qlm use qwen3.8-27b`, whose agent profile needs 20.8 GiB.
- **MTP fallback rule.** Agent runs with MTP off only if the draft fails to load on the pinned llama.cpp, or no configuration with the draft reaches 32,768 tokens of context while passing `qlm smoke`. Neither happened on b11669, so MTP is on. `qlm fetch` downloads the draft either way.
- **No vision for this model yet.** With 35B selected, `qlm profile use vision` and `qlm start vision` exit 2 with `the vision profile is not available for qwen3.6-35b-a3b`, and `qlm fetch --vision` exits 2 with `no vision files for qwen3.6-35b-a3b`. Adding vision needs a pinned projector that matches this model, and new measurements.
- Changing a pin, a profile's context or `--n-cpu-moe` needs new readings and an update to this ADR. A test compares the pins table above with `qlm/pins.py`.
